# Stage 3.2 — защищённый экспорт персональных данных

## Назначение

Пользователь может открыть **Личный кабинет → Скачать мои данные**, повторно подтвердить текущий пароль и получить один машиночитаемый JSON-файл. Это экспорт для переносимости и проверки данных, а не файл восстановления базы. Для восстановления конкретного пространства по-прежнему используется JSON-backup в настройках пространства.

## Состав файла

- данные аккаунта и профиля;
- собственные memberships и полученные приглашения без invitation token;
- настройки dashboard и уведомлений;
- пользовательские уведомления и безопасные сведения о подключённых устройствах;
- техническая активность AI без текста вопросов и редактированная проекция журнала безопасности;
- полные финансовые данные пространств, которыми пользователь владеет;
- только записи, созданные текущим пользователем, в пространствах других владельцев.

Осознанно исключены пароли, password proofs, JWT, cookies, CAPTCHA, API-ключи, одноразовые Telegram/invitation tokens, Web Push endpoint, `p256dh` и `auth`, а также профили остальных участников.

## Защитные свойства

1. В браузере выполняется password step-up. PostgreSQL повторно проверяет наличие password AMR не старше 5 минут и живой `auth.sessions`.
2. Edge Function читает экспортируемые строки через anon client с JWT пользователя. Service role не читает экспортируемые таблицы, поэтому все RLS-политики остаются обязательными.
3. Не более 3 экспортов на пользователя за скользящие 24 часа; идентификатор rate-limit хранится как HMAC.
4. Не более 100 000 строк и 32 МБ в одном файле. При превышении пользователь получает предложение скачать отдельные backup-файлы пространств.
5. JSON формируется в памяти Edge Function, сразу возвращается браузеру с `Cache-Control: no-store` и не записывается в Storage или временный файл.
6. Успех, блокировка и техническая ошибка записываются как `data.export.account`; журнал хранит только ограниченные безопасные метаданные.

## Проверка перед production

```powershell
npm run verify:release
```

После одобренной миграции и deploy:

1. Redeploy `privacy-export` с JWT verification.
2. Запустить production security smoke: он проверит разрешённый и hostile CORS preflight.
3. Войти тестовым пользователем, открыть личный кабинет и нажать **Скачать JSON**.
4. Убедиться, что без повторного пароля экспорт не запускается.
5. Проверить `format = fintrack-account-privacy-export`, `version = 1` и отсутствие строк `invitation_token`, Web Push endpoint/keys и любых JWT.
6. Проверить событие `data.export.account` запросами из `spec_fintrackapp/security_event_audit_queries.sql`.

Production load test не требуется и не должен выполняться.
