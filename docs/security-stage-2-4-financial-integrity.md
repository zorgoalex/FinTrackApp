# Этап 2.4 — идемпотентность финансовых записей и квоты PostgreSQL

Дата локальной реализации: 2026-08-23. Production, `main` и удалённые сервисы не изменялись.

## Результат

Поддерживаемые пути создания операции, перевода и подтверждения импорта получили payload-bound idempotency key. Повтор того же незавершённого запроса возвращает исходный результат, а повторное использование UUID с другим payload отклоняется. Операции, обе стороны перевода, теги, импортная сессия, строки импорта и receipt фиксируются одной транзакцией.

Прямые записи через authenticated PostgREST остаются разрешены в пределах RLS, но теперь не могут обойти per-workspace квоты: счётчики и отказ сверх лимита выполняются атомарными PostgreSQL-триггерами.

## Контракт идемпотентности

- Web UI создаёт UUID один раз для логического запроса, повторно использует его после сетевой или серверной ошибки и меняет после успешной записи либо изменения payload.
- API требует UUID в `Idempotency-Key` для `POST /operations` и `POST /transfers`. Заголовок разрешён общей CORS-политикой.
- PostgreSQL сериализует одинаковые `(user_id, request_id)` через transaction advisory lock.
- Receipt связан с workspace, типом запроса и SHA-256 payload. Несовпадение любого параметра завершает запрос ошибкой без финансовой записи.
- Receipt хранится семь дней. Каждый новый write удаляет до 100 истёкших receipts, поэтому служебная таблица очищается постепенно и без тяжёлой cron-задачи.
- Импорт дополнительно сохраняет прежнюю атомарную защиту по `import_fingerprint`.

Служебные receipts и счётчики находятся в схеме `private`, имеют RLS и не доступны ролям `anon`, `authenticated` и напрямую `service_role`.

## Остаточные ограничения

1. После истечения семидневного receipt тот же UUID может быть обработан заново. Клиент не должен переиспользовать старые UUID.
2. Идемпотентность защищает поддерживаемые UI/API/RPC entrypoints. Прямая PostgREST-вставка с новым намеренным payload не считается дублем, но RLS и квоту обойти не может.
3. Квоты считаются по строкам, а не по байтам. Лимиты размера upload/body и внешних ответов остаются отдельной защитой этапа 2.3.
4. Этапы 2.1 (production IDOR/BOLA/RLS pentest) и 2.2 (input/XSS/injection/SSRF) ранее отложены и этим этапом не заменяются.
