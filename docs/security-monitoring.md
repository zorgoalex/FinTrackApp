# Мониторинг безопасности и реагирование на инциденты

FinTrackApp хранит события безопасности в production PostgreSQL проекта Supabase, в таблице `private.security_events`. Схема `private` недоступна ролям `anon`, `authenticated` и для прямого чтения ролью `service_role`. Браузер может отправить только три разрешённых события экспорта через Edge Function `security-event`; функция повторно проверяет пользователя, активное членство и роль. Изменения ролей/участников, удаление и восстановление пространства, отмена приглашения и удаление аккаунта фиксируются непосредственно функциями или триггерами базы данных.

В журнал не попадают пароли, JWT, CAPTCHA-токены, cookie, заголовки авторизации, email, IP-адреса и ключи доступа. Идентификаторы входа и приглашения заменяются разделённым по назначению HMAC-SHA256. Метаданные допускают только скалярные значения, ограничены по размеру и проверяются на запрещённые имена. Срок хранения — 90 дней. Журнал входит в существующий зашифрованный production backup.

## Безопасный просмотр

Журнал просматривает только владелец проекта через Supabase SQL Editor. Нельзя публиковать схему `private` через Data API или добавлять RPC чтения для браузера.

```sql
select
  occurred_at,
  event_type,
  outcome,
  actor_user_id,
  target_user_id,
  workspace_id,
  source,
  metadata
from private.security_events
where occurred_at >= now() - interval '7 days'
order by occurred_at desc
limit 500;
```

Поводы для проверки: серии `blocked`/`failure`, неожиданные изменения ролей или состава участников, экспорты в необычное время, удаление/восстановление пространства и удаление аккаунта. Одна неудачная попытка входа не является инцидентом; серия по одному `subject_hash` может им быть.

## Автоматический production-монитор

`.github/workflows/production-security-monitor.yml` запускается каждые шесть часов и после релевантных изменений в `main`. Он проверяет production security headers, `security.txt`, недоступность типовых секретных путей и разрешённые/враждебные CORS preflight-запросы ко всем браузерным Edge Functions. Ошибка остаётся в GitHub Actions. Если в репозитории уже настроены `RESEND_API_KEY`, `BACKUP_ALERT_TO` и `NOTIFICATION_FROM_EMAIL`, workflow также отправляет письмо без нового платного сервиса или новых секретов.

## Реагирование на инцидент

1. Сохранить неуспешный GitHub Actions run и его время. Не копировать секреты в issue или чат.
2. Проверить последние семь дней `private.security_events` запросом выше, определить UUID пользователей/пространств и повторяющиеся HMAC-идентификаторы.
3. При подозрении на захват аккаунта отозвать затронутые Supabase-сессии и потребовать смену пароля. Ротировать секрет только при признаках его раскрытия.
4. При подозрении на нарушение авторизации или изоляции данных отключить затронутую Edge Function/функцию приложения, сохранить зашифрованные backup и не удалять доказательства до определения масштаба.
5. Исправить и проверить локально, выполнить SQL/application security gates, развернуть и вручную перезапустить **Production security monitor**.
6. Отдельно зафиксировать хронологию, масштаб, действия и итог проверки. Технический журнал не заменяет карточку инцидента.

Очистка запускается ежедневно при наличии `pg_cron`. Каждая запись события также удаляет строки старше 90 дней, поэтому срок хранения ограничен и в бесплатной/локальной среде без планировщика.
